# Deployment record: Google Cloud Run

**Date:** 2 November 2026  
**Platform:** Cloud Run  
**Region:** `us-east1`  
**Service:** Kubernetes Investigation Agent  
**Status:** Deployed and validated by the author

## Objective

Deploy the same Kubernetes Investigation Agent as a containerized HTTP service
to understand the operational model of Cloud Run alongside Agent Runtime.

## What was deployed

- The application's FastAPI service and A2A routes.
- A container image built from the repository's [`Dockerfile`](../../Dockerfile).
- Cloud Run infrastructure defined in
  [`deployment/terraform/single-project/`](../../deployment/terraform/single-project/),
  including service identity, logging storage, service configuration, networking,
  and telemetry settings.
- The same ADK agent, tools, incident samples, and evaluation assets used by the
  Agent Runtime deployment.

## Cloud Run configuration captured in source

The Terraform configuration documents the infrastructure choices made for the
exercise, including:

- a dedicated service account;
- a Cloud Run service in the configured region;
- concurrency and autoscaling boundaries;
- VPC egress configuration;
- telemetry/log export configuration; and
- a lifecycle rule that lets an external deployment process update the container
  image without Terraform overwriting it.

Configuration is intentionally tracked as source instead of committing
Terraform state, credentials, or a live service URL.

## Architecture

```text
HTTP or A2A client
       |
       v
Cloud Run service (containerized FastAPI application)
       |
       v
Google ADK agent and Kubernetes investigation tools
       |
       +-- structured log parsing
       +-- failure-signature detection
       +-- evidence-backed remediation report
```

## Validation approach

The deployment was validated with the same Kubernetes incident scenarios used
by this repository's local and evaluation workflows. The relevant source is
kept in [`tests/`](../../tests/) and [`sample_logs/`](../../sample_logs/), making
the service behavior inspectable even when the temporary cloud deployment is no
longer active.

## Why Cloud Run

Cloud Run was used to learn the container-based deployment path. It provides
control over the HTTP service, container lifecycle, ingress, networking,
scaling, and runtime configuration. That flexibility comes with responsibility
for clearly defining and operating those service-level concerns.

## What I learned

- Cloud Run makes the application boundary explicit: container image, HTTP
  interface, ingress, identity, scaling, and network configuration.
- Infrastructure as code is essential for explaining and recreating the
  deployment after temporary cloud resources are deleted.
- The same application can be deployed through different managed services when
  its interfaces, dependencies, and validation cases are clearly separated.
