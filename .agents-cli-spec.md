# Agent Spec

## Overview
The Kubernetes Investigation Agent is a single-agent Python application built with the Agent Development Kit (ADK). It accepts Kubernetes logs (either pasted directly in the prompt or loaded from a local log file) and investigates incidents using deterministic log-parsing and Kubernetes failure-signature detection tools. After completing its investigation, the agent produces a structured report containing:
1. **Executive Summary & Root Cause**: Clear identification of the primary failure mode and cascading effects.
2. **Supporting Evidence**: Verbatim log lines, line numbers, timestamps, error codes, and Kubernetes events extracted from the logs.
3. **Incident Timeline**: Chronological sequence of key events leading to the failure.
4. **Recommended Remediation**: Actionable diagnostic and remediation steps (e.g., `kubectl` inspection commands and manifest configuration fixes).

## Language
`python`

## Assumptions
- **Architecture**: Single ADK `Agent` (`root_agent`) equipped with deterministic Python tools for log parsing, Kubernetes failure signature detection, and local log file reading.
- **Deployment**: Prototype-first setup (`--prototype`) using the standard ADK Python template (`--agent adk`).
- **Cluster Access**: Self-contained log analysis only; no live Kubernetes cluster credentials or external cloud API authentication required.

## Example Use Cases
1. **Pasted Pod Crash / Memory Exhaustion Logs (`OOMKilled` & `CrashLoopBackOff`)**:
   - **Input**: User pastes raw container and pod event logs showing high memory allocation warnings followed by `State: Terminated, Reason: OOMKilled, Exit Code: 137` and `Back-off restarting failed container`.
   - **Output**: Structured report identifying container memory limit exhaustion (`Exit Code 137`) as the root cause, quoting the exact termination lines and timestamps under **Supporting Evidence**, reconstructing the restart timeline, and recommending `resources.limits.memory` adjustments and memory profiling.
2. **Application & Readiness Probe Failure from a Local Log File**:
   - **Input**: User asks the agent to investigate a local log file (e.g., `sample_logs/payment_service_crash.log`) containing `dial tcp 10.96.0.15:5432: connect: connection refused`, `Readiness probe failed: HTTP probe failed with statuscode: 503`, and `Back-off restarting failed container`.
   - **Output**: Structured report linking the upstream database connection refusal (`10.96.0.15:5432`) to the failing HTTP readiness probe (`503`), citing exact log lines and line numbers as supporting evidence, and providing targeted remediation steps to verify the database Service/Endpoints and probe configuration.
3. **Image Pull / Configuration Failure (`ImagePullBackOff` / `CreateContainerConfigError`)**:
   - **Input**: User pastes `kubectl describe pod` event logs showing `Failed to pull image "registry.example.com/app:v2.1.4": rpc error: code = NotFound` or `Error: secret "db-credentials" not found`.
   - **Output**: Structured report pinpointing the missing image tag or missing Secret, quoting the exact kubelet event messages as supporting evidence, and listing the exact verification/fix steps.

## Tools Required
- `parse_kubernetes_logs(log_text: str) -> dict`:
  - **Purpose**: Parses raw multi-line Kubernetes logs (container logs, `kubectl describe` output, or kubelet events) into structured metadata including line numbers, extracted timestamps, severity counts (`ERROR`, `WARN`, `FATAL`, `Warning`), affected pods/containers/namespaces, and a chronological event timeline.
  - **API & Auth**: Pure Python local processing; no external API or authentication required.
- `detect_k8s_failure_patterns(log_text: str) -> dict`:
  - **Purpose**: Scans log lines against a curated ruleset of Kubernetes failure signatures (`OOMKilled` / Exit Code 137, `CrashLoopBackOff`, `ImagePullBackOff` / `ErrImagePull`, Liveness/Readiness Probe failures, `CreateContainerConfigError`, DNS/Network timeouts & `connection refused`, RBAC `Forbidden`, Volume/PVC mount errors, and Node pressure/eviction) and returns matched failure categories along with verbatim supporting log lines and line numbers.
  - **API & Auth**: Pure Python local processing; no external API or authentication required.
- `read_log_file(file_path: str) -> dict`:
  - **Purpose**: Reads a local log file (`.log`, `.txt`, `.json`, `.out`) from the workspace so users can pass a file path for investigation.
  - **API & Auth**: Local filesystem read restricted to safe extensions within the project directory; no external auth required.

## Constraints & Safety Rules
- **Evidence-Grounded Analysis Only**: Every root-cause finding must cite verbatim log lines (with line numbers or timestamps) from the provided input. If the logs do not contain enough information to establish a definitive root cause, the agent must explicitly state that the root cause is inconclusive and list the additional logs/events required.
- **Read-Only Investigation**: The agent must never execute shell commands or mutate any cluster state; all `kubectl` commands and manifest changes are provided strictly as recommendations in the report.
- **Safe Local File Reading**: `read_log_file` must reject path traversal (`..`) outside the workspace directory and refuse to read sensitive files (e.g., `.env`, private keys, credentials).

## Success Criteria
- **Root Cause Identification**: Correctly identifies the primary failure mode in 100% of evaluation scenarios (`OOMKilled`, `CrashLoopBackOff`, `ImagePullBackOff`, probe/dependency failure, missing Secret/ConfigMap).
- **Supporting Evidence Citation**: 100% of generated investigation reports include a dedicated **Supporting Evidence** section containing verbatim log quotes from the input.
- **Tool Usage**: Invokes `parse_kubernetes_logs` and `detect_k8s_failure_patterns` (plus `read_log_file` when a file path is provided) during every log investigation turn.
- **Evaluation Score**: Passes `agents-cli eval run` across the evaluation dataset with rubric and trajectory scores meeting or exceeding the configured threshold (≥ 0.8).
